# Plan 11-03 — JSON Round-Trip for All 4 Log States

## Context

Phase 11 success criterion 2: "A JSON export-then-import cycle preserves all 4 log states without data loss or state coercion."

The export path reads all IDB stores via `exportJSON` in `js/io/export.js`. The import path merges via `mergeImportedStores` in `js/io/import.js` using merge-by-id (upsert, never delete). No existing test exercises this round-trip specifically for the 4 log statuses.

Log identity key: `[habitId, date]` (compound key in the `logs` IDB store).

The 4 states to verify:
1. `status: 'completed'` — binary log after markCompleted
2. `status: 'failed'` — binary log after markUncompleted
3. `status: 'skipped'` — binary log after markSkipped
4. No row (undefined) — habit has no log for that date

## Tasks

### Task 1 — Create log.4state.roundtrip.test.js

**File**: `tests/integration/log.4state.roundtrip.test.js` (new file)

Use `tests/helpers/fake-idb.js` as the IDB backend. Import `exportJSON` and `mergeImportedStores`/`configureImport` from the export/import modules (cache-busted with URL query params for isolation).

**Test structure:**

```js
describe('JSON export → import round-trip preserves all 4 log states', () => {
  // Setup: seed 4 log rows covering all states
  // Export to JSON
  // Parse JSON
  // Import into a fresh repo (new fake-idb instance)
  // Verify all 4 states survived
});
```

**Setup (before export):**

Seed the `logs` store in a fake repo with:
```js
{ habitId: 'h1', date: '2026-08-01', status: 'completed', definitionVersion: null }
{ habitId: 'h1', date: '2026-08-02', status: 'failed', definitionVersion: null }
{ habitId: 'h1', date: '2026-08-03', status: 'skipped', definitionVersion: null }
// No row for 2026-08-04 (undefined state — omission)
```

Also seed a minimal habit row in `habits` so the export includes it (exportJSON reads all 7 stores).

**Export step:**

Call `exportJSON(repo)` → returns a `Blob`. Read the Blob to a string, then `JSON.parse()` to get the export object. Verify the export object has a `logs` array containing 3 rows (not 4 — no row for the undefined date).

**Import step:**

Create a second fresh fake repo instance. Call `configureImport({ repo: freshRepo, broadcast: null })`. Call `mergeImportedStores(parsedExport)`. This should upsert all 3 log rows into `freshRepo`.

**Assertions:**

```js
// completed state preserved
const log1 = await freshRepo.getLog('h1', '2026-08-01');
assert.equal(log1.status, 'completed');

// failed state preserved
const log2 = await freshRepo.getLog('h1', '2026-08-02');
assert.equal(log2.status, 'failed');

// skipped state preserved
const log3 = await freshRepo.getLog('h1', '2026-08-03');
assert.equal(log3.status, 'skipped');

// undefined state preserved — no row
const log4 = await freshRepo.getLog('h1', '2026-08-04');
assert.equal(log4, undefined);
```

**Additional test — merge-by-id does not overwrite newer local edit:**

Seed a `status: 'completed'` row in `freshRepo` for `2026-08-03` before import. After importing the JSON (which has `status: 'skipped'` for that date), verify the row is overwritten with `status: 'skipped'` — this is the documented merge-by-id behavior (last import wins for colliding keys).

**Additional test — import is idempotent for non-colliding keys:**

Import the same JSON twice. Verify all 3 rows are still present with correct statuses (no duplication, no corruption).

**Pattern**: Use the same fake-idb + cache-bust pattern as other integration tests. See `tests/integration/export.integration.test.js` for the export setup pattern and `tests/integration/import.integration.test.js` for the import setup pattern.
