  <action>
Create a new file `data/convert-csv-to-import-2026-09-17.mjs` (do NOT edit
`data/convert-csv-to-import.mjs` — it is a historical artifact documenting how the 2026-08-27
import was built). Start from the same overall shape as `data/convert-csv-to-import.mjs` (already
in context) — reuse its `parseCSV`/`parseRow` CSV parser and its `normSkeleton` name-normalization
function verbatim, and reuse its `MANUAL_MAP` object verbatim (all 33 entries, keyed by CSV
column-0 ID, valued as an English name prefix) — the CSV row IDs are unchanged between the 08-27
and 09-17 exports, so the same map resolves the same encoding-ambiguous Polish names.

Three things must differ from the original script:

1. **Catalog source.** Load `data/habits-import-2026-08-27.json` (not
   `data/habits-2026-08-27.json`) via
   `JSON.parse(readFileSync(new URL('./habits-import-2026-08-27.json', import.meta.url), 'utf8'))`.
   Use its `habits` array directly as `realHabits` — every entry already carries a `startDate`, so
   skip the `.filter(h => h.startDate)` step the original script needed. Build `byNamePl` (keyed by
   `normSkeleton(h.name_pl ?? '')`) and `byEnglish` (keyed by `h.name`) lookup maps from this array,
   exactly as the original script does.

2. **TODAY constant.** Set `const TODAY = '2026-09-17';`.

3. **Date-column discovery (critical fix — do not port the original's offset arithmetic).** The
   current `Nawyki v1.csv` header row is NOT a clean contiguous run of date columns starting at a
   fixed index: it inserts an extra `"x"` column at header index 8 before dates begin at index 9,
   and — after the primary run of dates reaches 2027-01-03 — appends a second, duplicated block of
   date-shaped headers (indices 379-556, re-starting at 2025-12-30) whose data cells are all
   `#REF!` annotations. Because of this, the original script's pattern of
   `headers.slice(DATE_START).filter(dateRegex)` paired with `row[DATE_START + j]` would read the
   wrong column for the new file. Instead:
   - Parse the header row (`rows[0]`) once. Build an array of `{ i, d }` pairs — `i` = the
     header's absolute index in the row array, `d` = the header string — for every header matching
     `/^\d{4}-\d{2}-\d{2}$/`, walking the ENTIRE header row (not a slice from a fixed start).
   - Filter that array to entries where `d <= TODAY`, producing `activeDateCols`. (The duplicated
     second block is harmless to include in the initial full scan since its dates are all
     `<= TODAY` too, but its cells never contain exact `'1'`/`'0'` — verified empirically — so no
     special-case exclusion is needed; simply filtering by `d <= TODAY` and reading by absolute
     index is sufficient and correct.)
   - When extracting logs for a matched row, iterate `activeDateCols` and read
     `row[i]` (the pair's absolute column index) directly — never reconstruct a column position via
     `someOffset + arrayPosition` arithmetic.

Row-processing loop (rows 1..end of the parsed CSV): read `csvId = row[0]?.trim()`, skip if empty
or `'-99'`; read `namePl = row[3]?.trim() ?? ''`, skip if empty. Match precedence, identical to the
original script: (a) if `MANUAL_MAP[csvId]` exists, resolve via `findByEnglishPrefix` against
`byEnglish`; (b) otherwise fall back to `byNamePl.get(normSkeleton(namePl))`. If neither matches,
push `{ row, csvId, namePl }` to an `unmatched` array and continue (do not throw). If the resolved
habit's `id` is already in a `seen` Set, warn and skip (duplicate-match guard). Otherwise add the
habit id to `seen`, push the exact habit object (unmodified, from the catalog) to the output
`habits` array, then for each `{ i, d }` in `activeDateCols` read `val = (row[i] ?? '').trim()` and
push `{ habitId: habit.id, date: d, completed: true, definitionVersion: null }` when `val === '1'`,
or the same shape with `completed: false` when `val === '0'` — any other value (`x`, blank, `e*`,
`#REF!`, etc.) emits no log row.

After the loop: if `unmatched.length > 0`, `console.warn` each entry (row number, CSV id, name,
and its `normSkeleton` output) exactly as the original script's reporting does. Always
`console.log` a summary line with CSV row count, matched count, and unmatched count.

Write the output object — `{ schemaVersion: 1, habits, habit_versions: [], logs, events: [],
settings: [], meta: [], score_snapshots: [] }` — to
`data/habits-import-2026-09-17.json` via
`writeFileSync(new URL('./habits-import-2026-09-17.json', import.meta.url), JSON.stringify(output, null, 2), 'utf8')`,
then `console.log` a final summary of habit and log counts, matching the original script's closing
log style.

Add the same JSDoc file header style used by the original script and required by D-27
(`/** @file ... */` one-liner + rationale).
