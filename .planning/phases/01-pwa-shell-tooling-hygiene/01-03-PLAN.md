<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User input (pointer events) → diagnostics trigger | Long-press is the only user input that mounts the diagnostics panel from the mobile chrome |
| User confirm → Reset-shell destructive action | The `confirm()` dialog is the sole guard between an accidental click and an SW-unregister + caches-clear |
| Diagnostics-rendered values → DOM | All values rendered are author-controlled in P1, but the architecture must hold up when later phases render user data through the same surface |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-ResetSurface | Repudiation / Denial of Service | Reset-shell handler | mitigate | `confirm()` dialog with verbatim D-06 phrasing makes the destructive intent explicit. The action is logged via `console.log` only if researcher wants to add it (not required by ASVS L1). The recovery path is well-known: after reload, the SW re-registers and the cache repopulates from network. |
| T-01-V14 (long-press false-positive) | Denial of Service (UX) | `attachLongPress` | mitigate | Movement-tolerance check (`dx*dx + dy*dy > 100`) cancels the long-press timer if the user starts scrolling. Mitigates Pitfall 7 (diagnostics popping up unexpectedly during normal tap-and-scroll). |
| T-01-V14 (XSS hardening) | Tampering | All `textContent` usages | mitigate | Zero `innerHTML` with dynamic data. The toast and diagnostics modules render all dynamic values via `textContent` only. P1 has no user input, but the discipline lands here so P3+ (which renders user-content habit names through these primitives) inherits the safe pattern. |
| T-01-CacheScope (Reset-shell scope) | Tampering | Reset-shell handler | accept | The handler deletes ALL caches in `caches.keys()` (not filtered by `nawyki-` prefix). On a single-purpose static-PWA origin this is correct; if Nawyki ever shares an origin with another PWA (it will not — GH Pages sub-path isolation), filtering would be required. Accept per CONTEXT §Specifics and PROJECT.md single-origin model. |
| T-01-StaleCache (Check-for-update) | Tampering | "Check for update" button | mitigate | Manual trigger for `registration.update()` lets the developer force a freshness check without bumping APP_VERSION. Surfaces stale-cache states early. |
</threat_model>
