# Phase 13.1: Close gap: LOG4-02/LOG4-03 — Fail button deletes log instead of marking failed - Context

**Gathered:** 2026-09-18
**Status:** Ready for planning

<domain>
## Phase Boundary

Fix exactly two call sites where the swipe-left "Fail" action dispatches the wrong `apply()` event type. `js/views/today.js`'s `handleMarkFailTap` (Today view) and `js/views/history.js`'s `history-swipe-fail` handler (History view) both dispatch `apply({type:'markUncompleted', ...})` — whose handler (`js/state/apply/markUncompleted.js`) DELETES the log row, returning the habit-day to the undefined/not-logged state. They must instead dispatch `apply({type:'markFailed', ...})` — whose handler (`js/state/apply/markFailed.js`) already exists, is already registered in the `HANDLERS` table, and correctly writes `{status:'failed'}`. This closes the real gap behind LOG4-02 (Today) and LOG4-03 (History), both of which Phase 12 marked complete without this bug being caught.

</domain>

<decisions>
## Implementation Decisions

### Bug scope (confirmed via grep across `js/`)

- **D-01:** Exactly two call sites are in scope: `js/views/today.js:410` (inside `handleMarkFailTap`) and `js/views/history.js:385` (inside the `history-swipe-fail` action handler). Both currently read `apply({ type: 'markUncompleted', payload: { habitId, date } })` and must change to `apply({ type: 'markFailed', payload: { habitId, date } })`. — **Reversibility:** reversible

- **D-02:** The other three `markUncompleted` call sites are OUT of scope — they are correct as-is, not part of this bug:
  - `js/views/today.js:244` (`handleMarkUncompleteTap` — the plain tap-to-uncomplete button on an already-completed row; legitimately resets to undefined)
  - `js/views/history.js:356` (`toggle-log` handler's uncomplete branch — same legitimate reset semantics)
  - `js/views/today.js`'s `_swipeCycleLog` skipped→undefined wrap-around step (uses `markUncompleted` intentionally to delete the row and complete the cycle back to undefined)

- **D-03:** No data-recovery or historical-backfill work. The bug has been live since Phase 12 shipped (2026-09-01); any habit-day the user swiped "Fail" on in that window was silently deleted (now indistinguishable from "never tracked") with no audit trail to recover from. This phase is a silent forward-only fix — no changelog note, no PROJECT.md decision-log entry about the data loss. — **Reversibility:** one-way — the historical data loss itself cannot be undone; only the code path is being fixed going forward.

### Stale doc/comment correction (mechanical, alongside the fix)

- **D-04:** `handleMarkFailTap`'s JSDoc comment in `today.js` currently reads "dispatches `markUncompleted` (status → 'failed')" — inaccurate under both the old and new code (it never wrote `status:'failed'`; it deleted the row). Update the comment text to say `markFailed` once the dispatch is corrected, so the doc and code agree. — **Reversibility:** reversible

### TDD approach

- **D-05:** Follow the existing `tests/integration/today.tap.test.js` pattern (hand-rolled fake-document + `createFakeRepo()` fake IDB + real `apply.js`/`store.js`/`today.js` modules wired together) to add a RED test that clicks the `data-action="swipeFail"` button and asserts the log row afterward has `status: 'failed'` (not `undefined`/deleted). Mirror the same pattern for History's `history-swipe-fail` handler. No new DOM/test infrastructure needed — the swipe actions-panel buttons are always present in the rendered DOM (visibility is CSS-only via the `today-row--swipe-open` class), so tests can `.click()` them directly without simulating pointer drag gestures.

### Requirements bookkeeping

- **D-06:** (Claude's discretion, confirmed no objection raised) Once the fix lands and is verified, this phase should update `.planning/REQUIREMENTS.md` (LOG4-02, LOG4-03 rows and Traceability table) and `PROJECT.md` (move LOG4-02/LOG4-03 from Active to Validated, add phase reference "Phase 13.1") since Phase 12 marked these complete prematurely — the actual swipe-Fail behavior was never correct until this phase.

### Claude's Discretion

- Whether the RED/GREEN test additions land in `today.tap.test.js` / a new `history.tap.test.js`-style file, or a dedicated `tests/integration/swipe-fail.test.js` covering both views — either is fine as long as the pattern in D-05 is followed.
- Exact wording of any commit/PR description mentioning the historical data-loss window (D-03) — informational only, not a blocking decision.
