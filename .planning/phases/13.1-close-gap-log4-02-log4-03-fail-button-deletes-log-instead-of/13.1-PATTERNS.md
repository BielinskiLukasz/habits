## Shared Patterns

### Apply Event Dispatch

**Source:** `js/state/apply.js` (dispatch chokepoint)

All three handlers (`handleMarkSkipTap`, `handleMarkFailTap`, `history-swipe-fail`) use the same `apply()` call pattern:

```javascript
await apply({ type: 'markSkipped'|'markFailed'|'markUncompleted', payload: { habitId, date } });
```

The handler registration ensures the event type string matches a `HANDLERS[type]` entry that reads/writes the log row correctly.

### Undo & Toast Pattern

**Source:** `js/views/today.js` lines 218-221 and `js/views/toast.js`

Both fixed handlers use:
```javascript
const habitName = getCachedHabits().find((h) => h.id === habitId)?.name ?? '(habit)';
showUndoToast({ 
  message: t('today.markedNotDone', { name: habitName }), 
  undoFn: () => undo() 
});
```

The `habitName` read MUST happen post-`await apply()` (after `notify()` refreshes the cache per Pitfall 2); it reads from `getCachedHabits()` which was subscribed and re-hydrated by the store's notify call.

### Error Handling Pattern

**Source:** `js/views/today.js` lines 222-226

All handlers follow the same try/catch:
```javascript
try {
  await apply({ type: '...', payload: { habitId, date } });
  // success path: undo toast
} catch (_err) {
  showErrorToast(t('today.errorMark'));  // or 'history.errorMark'
}
```

The error toast is NOT re-rendered by a store.subscribe call; it is dispatched immediately as user feedback. The DOM is left in its pre-optimistic state (or reverted by the `revertRow` pattern used in tap handlers, not applicable here for swipe actions).
