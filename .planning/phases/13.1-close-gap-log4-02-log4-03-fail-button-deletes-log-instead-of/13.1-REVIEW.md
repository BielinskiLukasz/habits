# Phase 13.1: Code Review Report

**Reviewed:** 2026-09-18
**Depth:** standard
**Files Reviewed:** 4
**Status:** issues_found

## Summary

The narrow fix this phase targeted (swipe-Fail dispatching `markFailed` instead
of `markUncompleted` in both `js/views/today.js` and `js/views/history.js`) is
correct and minimal — verified against `git show` for both fix commits (one
line changed per file) and covered by the new regression test
`tests/integration/swipe-fail.test.js`, which is well-constructed and mirrors
the existing `today.tap.test.js` fake-DOM harness.

However, reviewing the full files (not just the diff) surfaced a **separate,
more severe data-loss bug in the same swipe-gesture code path** that this
phase did not touch: the generic pointer-swipe delegation wired for the
Today list (`js/views/today.js`) locates the habit to act on via a
non-specific `row.querySelector('[data-habit-id]')`, which also matches the
increment/decrement buttons on numeric rows and the slot-toggle controls on
slot-checklist rows (`js/views/today/builders.js`). A horizontal swipe
gesture that starts anywhere over those controls dispatches a **binary**
`markCompleted`/`markFailed`/`markSkipped`/`markUncompleted` event for that
habit — and because the corresponding apply handlers `put()` a full
replacement log row containing only `{habitId, date, status,
definitionVersion}`, this **silently destroys the habit's `count` or
`slots` progress for that day** (IndexedDB `put` overwrites the whole
record; there is no merge). This directly contradicts the project's stated
core value ("History integrity... habit-definition edits never rewrite
historical logs" / "the system's existing model... must be honored exactly")
and is classified Critical below.

Several smaller quality/consistency issues were also found: inconsistent
error handling (silent failure vs. toast) between sibling action handlers in
`history.js`, a stale docstring in `history.js` describing the exact class
of doc/code drift that caused the bug this phase fixed, hardcoded
non-localized aria-label strings in `today/builders.js` that bypass the
project's `t()` i18n convention, and dead code/stale documentation in
`buildFooterNav`.

## Critical Issues

### CR-01: Swipe gesture on numeric/slot rows mistargets habit and overwrites (destroys) count/slot log data

**File:** `js/views/today.js:337-362` (root cause), interacting with `js/views/today/builders.js:282-324` and `js/views/today/builders.js:340-412`

**Issue:**
The pointer-swipe listeners (`handleSwipeStart`/`handleSwipeMove`/`handleSwipeEnd`)
are attached once, unconditionally, to the whole `<ul class="today-list">`
(`js/views/today.js:630-634`), and apply to **every** row regardless of
`habit.targetType` — binary, numeric, and slot-checklist rows all carry the
`today-row` class that `handleSwipeStart` matches on (`js/views/today.js:298`,
confirmed by the classes built in `js/views/today/builders.js:290` and
`:382`).

When a swipe-right gesture (`dx > 60`) completes, the habit id used to
commit the action is resolved generically:

```js
// js/views/today.js:347
const habitId = row.querySelector('[data-habit-id]')?.getAttribute('data-habit-id');
if (habitId) _swipeCycleLog(habitId);
```

`buildNumericRow` (`js/views/today/builders.js:282-324`) renders a
decrement button and an increment button that both carry
`data-habit-id="<habit.id>"` (lines ~305-320), with no `.today-row__slide`
wrapper at all. `buildSlotRow` (`js/views/today/builders.js:340-412`)
similarly renders `toggle-slot` checkboxes and a `toggle-slots` button that
all carry `data-habit-id`. None of these controls is excluded by
`handleSwipeStart`'s guard (`js/views/today.js:302`, which only excludes
`.today-row__actions`, a class that exists only on binary rows).

Net effect: a horizontal swipe gesture that begins over a numeric row's
+/− buttons, or a slot row's toggle controls, matches the *first*
`[data-habit-id]` element in that row (the decrement button, or a slot
toggle) and calls `_swipeCycleLog(habitId)` — which dispatches
`markCompleted` / `markFailed` / `markSkipped` / `markUncompleted` for that
habit, exactly as if it were a binary habit.

The apply handlers for these events perform a full-record `put`, not a
merge — e.g. `handleMarkCompleted` (`js/state/apply/markCompleted.js:56-57`):

```js
const next = { habitId, date, status: 'completed', definitionVersion: null };
```

and `handleMarkFailed` (`js/state/apply/markFailed.js:35`) is identical in
shape. Neither preserves an existing `count` or `slots` field. Since IDB
`put()` replaces the whole record for the `(habitId, date)` key, any
`count`/`slots` progress already logged for that numeric/slot habit that
day is **silently wiped and replaced with a bare status row** — a real data
loss bug reachable through ordinary swipe interaction (very plausible on
touch devices, where a thumb naturally starts a drag over the visible
+/− or ▼ controls).

Additionally, because `buildNumericRow`/`buildSlotRow` render `isComplete`
purely from `count >= target` / `checkedCount >= total` and never read
`log.status`, the corrupted `status` field is invisible in the UI —
increasing the risk that the corruption goes unnoticed until, e.g., a CSV
export or scoring snapshot reads the polluted log row.

**Fix:**
Scope the swipe-commit lookup to the canonical binary tap button instead of
any element carrying `data-habit-id`, and/or bail out early for non-binary
rows:

```js
// js/views/today.js — handleSwipeEnd
if (dx > 60) {
  if (slide) slide.style.transform = '';
  // Only binary rows expose `.today-row-tap`; numeric/slot rows must not
  // be swipe-committed through the binary status cycle.
  const tapBtn = row.querySelector('.today-row-tap');
  const habitId = tapBtn?.getAttribute('data-habit-id');
  if (habitId) _swipeCycleLog(habitId);
}
```

Alternatively (and additionally, for defense in depth), guard
`handleSwipeStart` so numeric/slot rows never enter swipe tracking at all:

```js
function handleSwipeStart(evt) {
  if (evt.pointerType === 'mouse' && evt.button !== 0) return;
  const row = evt.target.closest('.today-row');
  if (!row) { _closeOpenSwipeRow(); return; }
  if (row.classList.contains('today-row--numeric') || row.classList.contains('today-row--slot')) return;
  if (evt.target.closest('.today-row__actions')) return;
  ...
}
```

Add a regression test asserting that a swipe-right gesture over a numeric
row's decrement button does not mutate `log.count` or introduce a `status`
field on that log row.

## Warnings

### WR-01: `history.js` toggle-log handler silently swallows errors (no user feedback)

**File:** `js/views/history.js:344-364`
**Issue:** The `toggle-log` action handler catches `apply()` rejection with
`catch (_e) { // Swallow — re-render will show current state }` and shows no
toast. Its sibling handlers in the same file, `history-swipe-skip` (`:365-378`)
and `history-swipe-fail` (`:379-392`), both call `showErrorToast(...)` on
failure. This is an inconsistent, silent-failure UX: a user tapping the
toggle button gets no indication that their action failed (e.g. on a
transient IDB error), while a user swiping gets a clear toast.
**Fix:** Call `showErrorToast(t('history.errorMark'))` in the catch block,
matching the pattern used by the swipe handlers in the same file.

### WR-02: Bulk "mark all not completed" silently swallows per-habit failures

**File:** `js/views/history.js:317-323`
**Issue:**
```js
for (const { habit } of notYetCompleted) {
  try {
    await apply({ type: 'markFailed', payload: { habitId: habit.id, date: selectedDate } });
  } catch (_e) {
    // Swallow — re-render will show current state
  }
}
```
If `apply()` throws for one habit mid-loop (e.g. a transaction conflict),
the loop continues silently and the user is never told that habit was not
marked. There is no toast, no count of failures, nothing — the user has to
notice a missing row change on their own.
**Fix:** Accumulate failures and surface a single summary toast (e.g.
`showErrorToast` with a count) when `notYetCompleted.length > 0` and at
least one `apply()` call rejected.

### WR-03: Stale docstring in `history.js` describes the same doc/code drift class that caused LOG4-02/03

**File:** `js/views/history.js:307-311`
**Issue:** The comment above the bulk handler reads:
```js
// HISTORY-04: mark all applicable-but-uncompleted habits as completed:false.
```
but the code dispatches `apply({ type: 'markFailed', ... })` (`:319`), not a
`completed:false` write — `completed:false` is not even a field this 4-state
log model uses anymore. This is exactly the failure mode this phase's fix
addressed elsewhere (a docstring claiming one dispatch semantics while the
code does another, per the `9d3f52c`/`9c6eb34` commit messages). Left
uncorrected, it is a landmine for the next person who "fixes" this handler
to match the (wrong) comment.
**Fix:** Update the comment to state the actual behavior: "mark all
applicable-but-not-yet-completed habits as `status: 'failed'` for the
selected date."

### WR-04: Hardcoded, non-localized aria-label strings bypass the project's `t()` i18n convention

**File:** `js/views/today/builders.js:308, 318, 401`
**Issue:** `buildNumericRow` and `buildSlotRow` build their control
aria-labels as raw English template literals:
```js
'aria-label': `Decrease count for ${habit.name}`,
'aria-label': `Increase count for ${habit.name}`,
'aria-label': `Toggle slots for ${habit.name}`,
```
This file's own header states "Adopts i18n via t() import for all
user-visible strings (I18N-02)" and every other user-facing string in this
file (`t('today.skip')`, `t('today.showPolish')`, etc.) goes through `t()`.
These three do not, so a Polish-language user gets an English aria-label
read by their screen reader. They also use `habit.name` instead of the
already-computed `displayName` (which resolves `habit.name_pl` in PL mode)
used everywhere else in the same function, compounding the inconsistency.
**Fix:** Route these through `t()` with an interpolated name, e.g.
`t('today.decreaseCountFor', { name: displayName })`, matching the pattern
used for `today.showPolish`.

### WR-05: `history.js` async `render()` has no guard against overlapping/out-of-order completions

**File:** `js/views/history.js:212-260`
**Issue:** `render(date)` synchronously clears `parent` then does three
sequential `await`s (`repo.getLogsForDate`, `repo.getAllHabits`, and one
`repo.getHabitVersionAtDate` per habit) before mounting anything. Every
action handler in this file (`toggle-log`, `history-swipe-skip`,
`history-swipe-fail`, `bulk-mark-uncompleted`, prev/next/pick-date) calls
`render(selectedDate)` again after its own `await apply(...)` resolves, with
no generation token or in-flight guard. Two swipe/tap actions fired in quick
succession (e.g. a fast double-swipe on two different rows, or a stray
duplicate event) can produce two overlapping `render()` calls whose
`clearChildren` + mount cycles interleave, so the DOM ends up reflecting
whichever call's awaits happen to resolve last — not necessarily the most
recent user action.
**Fix:** Introduce a monotonically increasing render token; capture it at
the top of `render()` and bail out before mounting if a newer render has
started in the meantime:
```js
let _renderToken = 0;
async function render(date) {
  const myToken = ++_renderToken;
  ...
  const logsForDate = await repo.getLogsForDate(date);
  if (myToken !== _renderToken) return; // superseded
  ...
}
```
