## Context

### DI Seam for apply.js → scoreSnapshots (avoiding circular imports)

`apply.js` is the single mutator chokepoint. After every log-mutating event, it must call `writeHabitSnapshots(habitId, repo)`. However, importing `scoreSnapshots.js` from `apply.js` would create a potential circular dependency (`scoreSnapshots.js → scoring.js → date.js`, while `apply.js → apply/markCompleted.js → ...`). The safe approach: extend the existing `configure()` DI seam in `apply.js` with an `onLogWrite` callback:

```javascript
// In apply.js:
let _onLogWrite = async (_habitId) => {};  // no-op by default

export function configure(deps) {
  // ... existing fields ...
  if (deps.onLogWrite) _onLogWrite = deps.onLogWrite;
}
```

In `apply()`, after `await _notify(...)`:
```javascript
if (keys && keys.habitId) {
  await _onLogWrite(keys.habitId);
}
```

In `desktop.js` and `main.js` boot, call:
```javascript
import { writeHabitSnapshots } from './io/scoreSnapshots.js';
configureApply({
  repo, broadcast, trackTx,
  onLogWrite: async (habitId) => { await writeHabitSnapshots(habitId, repo); },
});
```

**Log-mutating event types** (those where `keys.habitId` is populated):
- `markCompleted`, `markUncompleted`, `restoreLogRow`, `logNumeric`, `logSlot`

These handlers already call `.broadcastKeys(event)` which returns `{ habitId, date }`. The `keys.habitId` check naturally gates non-log events (like `setSetting` which returns `{ key }` without `habitId`).

### Settings builders additions (D-122, D-123)

**New builder: `buildScoringModelCard({ scoringModel })`**
- `scoringModel`: `'S1'|'S2'|'S3'` (current active model, read from settings store)
- Card structure mirrors `buildScheduleCard` (radio group pattern)
- Three radios sharing `name="scoringModel"` with values `'S1'`, `'S2'`, `'S3'`
- Each radio carries `data-action="setScoringModel"`
- Heading ID: `'settings-scoring-model-h2'`
- Label text: `'Scoring Model'`
- Radio labels: `'S1 — Rolling Threshold'`, `'S2 — Day-Weighted'`, `'S3 — Load-Adjusted'`
- The checked radio = the one matching `scoringModel`

**Extend `buildDataCard` to include Recompute button (D-123):**
- Add a new sub-block inside the Data card (after the Backup section, before the Undo section)
- New block: `<div class="settings-data-recompute">` containing:
  - A `<button data-action="recomputeScores" aria-label="Recompute Scores">Recompute Scores</button>`
  - Loading state (when `isRecomputing === true`): button has `disabled=""` attribute and text `"Recomputing…"`
  - `buildDataCard` signature gains `isRecomputing?: boolean` param (default `false`)

### Settings view wiring (js/views/settings.js)

The mounter needs to:
1. Mount the new `buildScoringModelCard` into the Settings panel (after Mastery card, before About card)
2. Handle `data-action="setScoringModel"` — on `change` event on any radio with `data-action="setScoringModel"`, dispatch `apply({type:'setSetting', payload:{key:'scoringModel', value: evt.target.value}})` — uses the existing `setSetting` handler, no new handler needed
3. Handle `data-action="recomputeScores"` — on click:
   a. Set UI loading state (re-render the Data card with `isRecomputing: true`)
   b. Call `rebuildAllSnapshots(repo, onProgress)` — import from `../../io/scoreSnapshots.js`
   c. After completion: show toast "Snapshots recomputed. All scores updated."
   d. Re-render Data card with `isRecomputing: false`
   e. Call `store.notify()` so desktop view subscribers refresh
4. Live-refresh the Scoring Model card on `store.notify()` (model switch → settings change → notify → re-render radio selection)
5. Add "Open desktop analytics →" link: in the About card or as a standalone `<p>` in the Settings panel, include an `<a href="./desktop.html">Open desktop analytics →</a>` link (D-115, DESKTOP-01)
