## v1 Requirements — All Shipped ✅

### CORE — Today view

- [x] **CORE-01**: User can open `index.html` on mobile and see today's scheduled habits without delay (cold paint < 300 ms) — v1.0 Phase 3
- [x] **CORE-02**: User can mark a habit complete with a single tap (binary habits) — v1.0 Phase 3
- [x] **CORE-03**: User can unmark a previously-completed habit with a single tap — v1.0 Phase 3
- [x] **CORE-04**: User can see, on Today, only the habits whose cadence rules say they apply today — v1.0 Phase 3
- [x] **CORE-05**: User sees today's date and current wave context displayed on Today — v1.0 Phase 3
- [x] **CORE-06**: Today view renders synchronously from a cached snapshot (no spinner-blocked first paint) — v1.0 Phase 3

### CATALOG — Habit definitions

- [x] **CATALOG-01**: User can create a new habit with: name, wave, cadence rule, target type, stage definitions — v1.0 Phase 4
- [x] **CATALOG-02**: User can edit an existing habit's definition — v1.0 Phase 4
- [x] **CATALOG-03**: Editing a habit creates a new `habit_versions` entry; prior version remains accessible — v1.0 Phase 4
- [x] **CATALOG-04**: User can view the full edit history of any habit — v1.0 Phase 4
- [x] **CATALOG-05**: User can archive a habit (stops appearing on Today; history preserved) — v1.0 Phase 4
- [x] **CATALOG-06**: User can restore an archived habit — v1.0 Phase 4
- [x] **CATALOG-07**: User can plan a new habit with a future `startDate` — v1.0 Phase 4

### CADENCE — Schedule rules

- [x] **CADENCE-01**: User can set a habit to daily cadence — v1.0 Phase 4
- [x] **CADENCE-02**: User can set a habit to weekly cadence — v1.0 Phase 4
- [x] **CADENCE-03**: User can set a habit to monthly cadence — v1.0 Phase 4
- [x] **CADENCE-04**: User can set a habit to "every N days" cadence — v1.0 Phase 4
- [x] **CADENCE-05**: User can restrict a habit to specific days of the week — v1.0 Phase 4
- [x] **CADENCE-06**: Cadence engine correctly identifies applicability for any combination of rules — v1.0 Phase 4
- [x] **CADENCE-07**: Cadence engine handles DST transitions, leap days, and month-end edge cases — v1.0 Phase 4

### STAGE — Progressive targets

- [x] **STAGE-01**: A habit can declare ordered stages (etap 1, etap 2, etap 3), each with its own target value — v1.0 Phase 4
- [x] **STAGE-02**: User can view the current stage of any habit — v1.0 Phase 4
- [x] **STAGE-03**: Stage advancement supports a "manual button" trigger — v1.0 Phase 4
- [x] **STAGE-04**: Stage advancement supports a "scheduled by week" trigger — v1.0 Phase 4
- [x] **STAGE-05**: Stage advancement supports an "after N days at current stage" trigger — v1.0 Phase 4
- [x] **STAGE-06**: A single habit can compose multiple stage triggers — v1.0 Phase 4
- [x] **STAGE-07**: Manual stage demotion is supported — v1.0 Phase 4

### MASTERY — Threshold-based graduation

- [x] **MASTERY-01**: Default mastery threshold is 90% completion over rolling 70 days, configurable globally — v1.0 Phase 4
- [x] **MASTERY-02**: Per-habit threshold and window can override the global defaults — v1.0 Phase 4
- [x] **MASTERY-03**: A habit that meets its threshold is displayed with a "mastered" visual treatment — v1.0 Phase 4
- [x] **MASTERY-04**: A mastered habit that drops below threshold reverts visual treatment — v1.0 Phase 4
- [x] **MASTERY-05**: Mastery is evaluated using cadence-aware denominator — v1.0 Phase 4
- [x] **MASTERY-06**: New habits enter a 7-day grace period — v1.0 Phase 4
- [x] **MASTERY-07**: Mastery is recomputed write-time — v1.0 Phase 4

### LOG — Multi-occurrence logging

- [x] **LOG-01**: User can configure a habit's logging UX as "binary" — v1.0 Phase 3
- [x] **LOG-02**: User can configure as "numeric +1 counter" — v1.0 Phase 4
- [x] **LOG-03**: User can configure as "slot-checklist" — v1.0 Phase 4
- [x] **LOG-04**: For slot-checklist habits, user can choose anonymous OR user-labeled slots — v1.0 Phase 4
- [x] **LOG-05**: Multi-occurrence habits show progress toward target — v1.0 Phase 4
- [x] **LOG-06**: Multi-occurrence habits count as "completed" only when target is reached — v1.0 Phase 4

### HISTORY — Past-day navigation and edits

- [x] **HISTORY-01**: User can navigate to any past day — v1.0 Phase 4
- [x] **HISTORY-02**: User can see habits that applied on any past day — v1.0 Phase 4
- [x] **HISTORY-03**: User can mark a habit as not-completed on a past day — v1.0 Phase 4
- [x] **HISTORY-04**: User can bulk-action "mark all not-yet-completed as uncompleted" — v1.0 Phase 4
- [x] **HISTORY-05**: Partial multi-occurrence completions are preserved as logged counts — v1.0 Phase 4
- [x] **HISTORY-06**: Logs for any past day are interpreted against the `habit_versions` entry effective that day — v1.0 Phase 4

### WAVE — Fala model and aggregates

- [x] **WAVE-01**: Each habit belongs to exactly one wave (Fala 0–9 seeded, future waves extensible) — v1.0 Phase 4
- [x] **WAVE-02**: Waves have a name, a date range, and a theme description — v1.0 Phase 4
- [x] **WAVE-03**: User can view aggregate metrics per wave: completion %, count by status — v1.0 Phase 4
- [x] **WAVE-04**: User can view "longest active wave streak" — v1.0 Phase 4
- [x] **WAVE-05**: User can see a "wave at risk" indicator — v1.0 Phase 4
- [x] **WAVE-06**: User can extend the wave model beyond 2026 — v1.0 Phase 4

### UNDO — Single-step undo

- [x] **UNDO-01**: User can undo the last mutating action within one tap from toast OR Settings — v1.0 Phase 3
- [x] **UNDO-02**: Undo state persists across page reload — v1.0 Phase 3
- [x] **UNDO-03**: Undo is single-step — v1.0 Phase 3

### DATA — Persistence and integrity

- [x] **DATA-01**: All habits, logs, edit history, and settings persist in IndexedDB across sessions — v1.0 Phase 2
- [x] **DATA-02**: IndexedDB schema is versioned with a `DB_VERSION` constant and `MIGRATIONS` dispatch table — v1.0 Phase 2
- [x] **DATA-03**: App calls `navigator.storage.persist()` on first write and surfaces persistence status in Settings — v1.0 Phase 2
- [x] **DATA-04**: All mutations go through a single chokepoint (`state/apply.js`); views never write to IDB directly — v1.0 Phase 2
- [x] **DATA-05**: Habit-definition edits never modify existing log rows — v1.0 Phase 2
- [x] **DATA-06**: Date keys are stored as local `YYYY-MM-DD` strings — v1.0 Phase 2
- [x] **DATA-07**: Cross-tab writes propagate via `BroadcastChannel('habits')` — v1.0 Phase 2 (wiring closed in audit)
- [x] **DATA-08**: App flushes pending writes on `visibilitychange → hidden` — v1.0 Phase 2

### EXPORT — JSON backup + CSV analytics export

- [x] **EXPORT-01**: User can download a full-fidelity JSON backup via Settings — v1.0 Phase 5 (wiring closed in audit)
- [x] **EXPORT-02**: JSON export embeds the current `schemaVersion` — v1.0 Phase 5
- [x] **EXPORT-03**: User can download a CSV habit × day completion matrix — v1.0 Phase 5
- [x] **EXPORT-04**: CSV export uses `;` separator, UTF-8 BOM, CRLF — v1.0 Phase 5
- [x] **EXPORT-05**: CSV export correctly preserves Polish diacritics — v1.0 Phase 5
- [x] **EXPORT-06**: CSV cells encode multi-occurrence habits as their numeric count — v1.0 Phase 5
- [x] **EXPORT-07**: CSV filename includes the export date — v1.0 Phase 5
- [x] **EXPORT-08**: User sees a "Last backup: N days ago" banner; weekly nag — v1.0 Phase 5

### IMPORT — JSON restore

- [x] **SCORING-03**: Switching models updates dashboards without reload — v1.0 Phase 6

- [x] **SCORING-05**: S2 computes momentum score with exponential day-weighting — v1.0 Phase 6
- [x] **SCORING-06**: S3 computes load-adjusted score — v1.0 Phase 6

- [x] **SCORING-08**: Scoring outputs persisted in `score_snapshots`; views read snapshots, never call scoring.js — v1.0 Phase 6
- [x] **SCORING-09**: Snapshots include `scoreVersion` field for algorithm recompute — v1.0 Phase 6
