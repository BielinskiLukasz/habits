## Symptoms

- **Expected behavior:** A weekly (or monthly) habit's current, still-open period should not count as a failure in S1 until that period has actually elapsed. A user should be able to complete a weekly habit any day during its ISO week without S1 already having marked that week as missed partway through.
- **Actual behavior:** `_computeS1Periodic` in `js/domain/scoring.js` iterates periods from `windowStart` to `ctx.evaluationDate`, clamping `effectiveEnd` to `ctx.evaluationDate` for the period containing today. As soon as `habit.startDate <= effectiveEnd`, it increments `expectedPeriods` for that in-progress period — before checking whether the period has actually finished (`pEnd > ctx.evaluationDate`). If no completion log exists yet within `[effectiveStart, effectiveEnd]` (i.e. the days-so-far of the current week/month), the period is counted as a miss in the denominator without a matching numerator increment, even though there are still days left in the period to log it. This deflates S1 score prematurely for weekly/monthly habits mid-period.
- **Error messages:** None — silent scoring miscalculation, not an exception.
- **Timeline:** Present since `_computeS1Periodic` was introduced (Bug 3 fix comment in the file, per D-110/SCORING-07). Reported by the user while reviewing S1 scores in the desktop waveboard/analytics views.
- **Reproduction:**
  1. Create a weekly-cadence habit with `startDate` in the past (grace period elapsed).
  2. Do not log it for the current, still-open ISO week (leave earlier weeks fully completed).
  3. Compute S1 (`computeS1`) with `ctx.evaluationDate` = a day mid-week, before the week's Sunday/end (per `ctx.weekStart`).
  4. Observe: `completedPeriods` does not include the current week (no completion yet), but `expectedPeriods` already includes it — so the current, still-completable week is already scored as a fail in the S1 ratio.
  5. Expected: the current, still-open period should not count toward the failure ratio until it has actually elapsed (`pEnd <= ctx.evaluationDate`) OR should count if already completed within the elapsed-so-far portion.

## Resolution

- root_cause: "TWO confirmed, independent causes discovered in series (each AND-gate: no individually — they are sequential/orthogonal defects, not conditions that had to co-occur):
    1. (algorithm, js/domain/scoring.js) `_computeS1Periodic` increments `expectedPeriods` for a period as soon as `habit.startDate <= effectiveEnd`, without ever checking whether the period has actually elapsed (`pEnd <= ctx.evaluationDate`). The still-open current week/month was counted as an expected-but-unmet period (a miss) before it could possibly be completed, prematurely deflating the S1 score for weekly/monthly-cadence habits mid-period. This is what made the score WRONG originally.
    2. (delivery-path, js/views/settings.js + js/desktop.js) `recomputeScores` propagated its post-recompute refresh signal via the CALLER-injected `store.notify`, guarded by `typeof store.notify === 'function'`, instead of the statically-importable canonical `notify` export from js/state/store.js (which the same file already used directly for `subscribe`). js/desktop.js's '#settings' route constructed a store object omitting `notify` (unlike js/main.js, which passes the full store module namespace). Because js/views/desktop/analytics.js and js/views/desktop/waveboard.js are idempotently mounted (D-115) and refresh ONLY via the store.subscribe fan-out triggered by notify(), a manual Recompute Scores click on the desktop shell correctly rewrote score_snapshots in IndexedDB but never told the already-mounted Analytics/Waveboard view to re-read it. This is what made root cause 1's fix APPEAR not to have taken effect during human verification (byte-identical stale score on the desktop shell)."
- fix: "Two fixes, one per root cause:
    1. js/domain/scoring.js (_computeS1Periodic, lines ~113-140): the completion search within [effectiveStart, effectiveEnd] now runs first into a `hasCompletion` boolean (unconditionally, still gated by the existing habit.startDate guard). expectedPeriods++ (and completedPeriods++ when hasCompletion) now only fire when `(pEnd <= ctx.evaluationDate)` [period fully elapsed] OR `hasCompletion` [early completion still credits].
