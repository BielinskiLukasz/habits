## waveboard-idb-databinding — all waveboard cells render as "na" due to IDBRequest non-iterable bug

- **Date:** 2026-08-27
- **Error patterns:** waveboard cells na, heat-map empty, TypeError snapshotRows not iterable, IDBRequest not iterable, runTx body returns IDBRequest, cachedCellData empty
- **Root cause(s):** waveboard.js called repo.runTx() with a body returning a raw IDBRequest (not a Promise); idb.js runTx does `await body(tx)` — IDBRequest is not thenable so await resolves to the IDBRequest object itself; for-of on the IDBRequest throws TypeError caught silently; cachedCellData stays empty; all cells render as waveboard-cell--na
- **Fix:** Added repo.getSnapshotsInRange(startYMD, endYMD) to js/db/repo.js following the getLogsInRange() pattern (uses indexGetAll — returns Promise<object[]>); waveboard.js refresh() replaced inline runTx block with repo.getSnapshotsInRange(); fake-idb.js and contract test updated
- **Files changed:** js/db/repo.js, js/views/desktop/waveboard.js, tests/helpers/fake-idb.js, tests/integration/contract.fake-vs-real.test.js, tests/integration/repo.snapshotsInRange.test.js
- **Why not caught:** no gate prevented direct use of runTx() with a body returning a raw IDBRequest; the pitfall was documented in repo.js JSDoc but not enforced; no test existed for the waveboard snapshot query path
- **Recurrence guard:** regression test at tests/integration/repo.snapshotsInRange.test.js — "result from non-empty store is iterable via for-of without throwing TypeError" (10 tests including boundary neighbours N±1, multi-habit, single-day range)

## phase-06-uat-11-history-names — seeded habits display post-edit name in history view

- **Date:** 2026-08-27
- **Error patterns:** historical habit names changed, history shows new name after edit, version undefined, getHabitVersionAtDate returns undefined, NFR-10, UAT-11, history integrity
- **Root cause(s):** seed.js never wrote rows to the `habit_versions` store; the runTx stores list omitted `habit_versions`; when a seeded habit was edited, the only version row had effectiveFrom=editDate (new name); getHabitVersionAtDate returned undefined for any date before the edit; history.js fell back to the current habit object (post-edit name)
- **Fix:** Added `habit_versions` to seed.js runTx stores list; writes initial version row per seeded habit (effectiveFrom = startDate ?? '0000-01-01'); added one-time backfill migration for existing databases gated by meta.habitVersionsSeeded
- **Files changed:** js/io/seed.js, tests/integration/seed.idempotent.test.js
- **Why not caught:** no test asserted that seeded habits had habit_versions rows; the NFR-10 (history integrity) invariant was tested at the editHabit layer but not at the seed layer; gap between createHabit (which correctly wrote versions) and seed (which bypassed the createHabit handler)
- **Recurrence guard:** regression test at tests/integration/seed.idempotent.test.js — "NFR-10 — each seeded habit gets an initial habit_versions row (UAT-11 fix)" (2 tests: first-run write + migration backfill)

## wave-completion-weekly-cadence — waveboard tooltip shows 0/7 or 1/7 for weekly habits instead of 1/1

- **Date:** 2026-09-16
- **Error patterns:** waveboard 0/7, waveboard 1/7, weekly cadence completion percentage wrong, wave analytics miscounts weekly habits, applicableToday inflated, loggedToday, cellTitle days ratio wrong, score_snapshots per-day summed across week
- **Root cause(s):** js/io/scoreSnapshots.js computed score_snapshots.applicableToday/loggedToday via a raw per-day cadence.appliesToday() call for ALL cadence types; for weekly/monthly cadence appliesToday's "still due this period?" semantics stay true on every day from the period's start through the day of completion (D-49/CADENCE-03 log-aware resolvers), so js/views/desktop/waveboard.js's per-ISO-week summation of that flag produced a denominator ranging 1-7 (weekly) depending on which weekday carried the completion, instead of the cadence-correct "1 occurrence per elapsed period."
- **Fix:** Added `_snapshotApplicability()` to js/io/scoreSnapshots.js mirroring the already-existing `_computeS1Periodic` pattern in js/domain/scoring.js: for weekly/monthly cadence, mark exactly one day per period as applicableToday=true (the period start, clamped forward to the snapshot range's start for habits created mid-period), with loggedToday=true iff any completed log falls within that period (clamped to today for the still-elapsed portion). Daily/day-of-week-subset/every-n-days cadences are untouched (unchanged raw per-day appliesToday() call), matching computeS1's own scoping decision.
- **Files changed:** js/io/scoreSnapshots.js, tests/unit/io/scoreSnapshots.test.js
- **Why not caught:** No test asserted applicableToday/loggedToday values for non-daily-cadence habits — tests/unit/io/scoreSnapshots.test.js only checked row *shape* (field presence) using daily-cadence fixtures, never a weekly/monthly fixture. The Phase 13 code review (QA-01, "all-clear") was scoped to the D-43 stale-boolean (`log.completed === true` vs `log.status`) pattern and did not re-check for the sibling "appliesToday summed per calendar day" denominator-inflation class that had ALREADY been identified and partially fixed elsewhere in the same file's sibling module (scoring.js's `_computeS1Periodic`, labeled "Bug 3 fix") — that earlier fix was never audited for other call sites reusing the same flawed pattern.
- **Recurrence guard:** regression test suite at tests/unit/io/scoreSnapshots.test.js — `describe('weekly/monthly cadence tooltip flags (wave-completion-weekly-cadence)')` (7 tests: completion on first vs last day of an elapsed week both resolve to 1/1, never-completed resolves to 0/1, a completion in the following period does not leak backward across the period boundary, mid-period habit creation anchors correctly, daily-cadence is provably unaffected, monthly cadence collapses correctly) — plus this knowledge-base entry, so a future Phase-0 match flags the "raw per-day appliesToday() summed for occurrence-counting" anti-pattern before it recurs in a new call site (e.g. if computeS2/computeS3 or the currently-unwired js/domain/waveAggregates.js are ever wired into a live view using the same flawed approach — both were found during this investigation to share the identical latent defect, out of scope for this fix).

## history-seed-null-startdate — seed habits with startDate:null show as applicable on pre-install historical dates

- **Date:** 2026-09-17
- **Error patterns:** history view shows demo habits on old dates, seed habits applicable before app existed, startDate null, createdAt missing, appliesToday no-op existence guard, habit.createdAt undefined, CATALOG-07 guard bypassed, history.js createdAt filter defeated
- **Root cause(s):** js/io/seed.js writes seed-catalog habit rows into the `habits` IDB store verbatim from seed/habits.json, which has no `createdAt` field, and all 8 seed habits also have `startDate: null` (not future-scheduled); js/domain/cadence.js's appliesToday() existence/future-scheduling guard checks only `habit.startDate` with no fallback to `habit.createdAt`, so the guard is permanently a no-op for these habits and the cadence resolver is consulted for any date whatsoever, including ones predating the app's installation. js/views/history.js's own separate `habit.createdAt > date` existence filter — added specifically to catch this case — is defeated by the identical missing field. (AND-gate: no — seed.js's missing write alone reproduces the reported symptom; the cadence.js guard fix closes the same gap for other direct appliesToday() consumers such as CSV export, which has no independent guard of its own.)
- **Fix:** (1) js/domain/cadence.js — existence guard extended to `const existenceAnchor = habit.startDate ?? habit.createdAt` (strict superset of prior behavior). (2) js/io/seed.js — first-run insert now stamps `createdAt: h.createdAt ?? todayLocal()`; added a one-time `createdAtBackfilled` migration for already-seeded installs (reads each habit's `seed:createHabit` event `at` timestamp, falls back to `startDate ?? todayLocal()`). Scope-expansion (user-confirmed): (3) js/io/seed.js — added `DEMO_HABIT_IDS` + a `demoHabitsRemoved` migration that hard-deletes a demo habit id when zero logs exist against it, else archives it (preserves history-integrity invariant); (4) seed/habits.json — demo habits array emptied to `[]` for fresh installs.
- **Files changed:** js/domain/cadence.js, js/io/seed.js, seed/habits.json, tests/unit/cadence.test.js, tests/integration/seed.idempotent.test.js, tests/integration/seed.persist.test.js, tests/unit/seed.shape.test.js
- **Why not caught:** No gate existed for this class. js/io/seed.js was the only habit-write path never covered by a test asserting `createdAt` is populated (js/state/apply/createHabit.js's equivalent contract IS tested). A near-miss existed: the prior phase-06-uat-11-history-names incident (same file, same write path — seed.js skipping a required per-habit field, that time `habit_versions`) was fixed without an audit for sibling fields skipped by the identical insert loop, so the same root shape of defect (seed.js insert loop omitting a field createHabit.js always sets) recurred here with `createdAt` instead of `habit_versions`.
- **Recurrence guard:** regression tests at tests/unit/cadence.test.js — `describe('appliesToday — createdAt existence-fallback guard (history-seed-null-startdate)')` (7 tests: blocks a past-relative-to-createdAt date, boundary N-1/N/N+1, startDate takes precedence over createdAt when both present, safe default when both absent, resolver short-circuited before being consulted) and tests/integration/seed.idempotent.test.js — `describe('bootSeed: createdAt forward-fix + backfill migration')` (5 tests) + `describe('bootSeed: demoHabitsRemoved migration')` (6 tests) + `describe('bootSeed: tolerates an empty seed/habits.json habits array')` (2 tests) — plus this knowledge-base entry, so a future Phase-0 match flags "seed.js insert loop omits a field createHabit.js always sets" as a recurring defect class before it strikes a third field.

## s1-weekly-period-premature — S1 score deflated for weekly/monthly habits mid-period; recompute appeared to do nothing on desktop

- **Date:** 2026-09-18
- **Error patterns:** S1 score too low, weekly habit scored as missed before week ends, monthly habit premature fail, Recompute Scores no effect, score unchanged after recompute, desktop waveboard stale score, computeS1 denominator wrong, expectedPeriods inflated
- **Root cause(s):** TWO independent causes found in series. (1) algorithm, `js/domain/scoring.js` — `_computeS1Periodic` incremented `expectedPeriods` for the current, still-open week/month as soon as `habit.startDate <= effectiveEnd`, without ever checking whether the period had actually elapsed (`pEnd <= ctx.evaluationDate`); this counted an in-progress, still-completable period as an immediate miss. (2) delivery-path, `js/views/settings.js` + `js/desktop.js` — `recomputeScores` propagated its post-recompute refresh signal via a caller-injected `store.notify`, guarded by `typeof store.notify === 'function'`, instead of the statically-importable canonical `notify` export (which the same file already used directly for `subscribe`); `js/desktop.js`'s `#settings` route built a store object that omitted `notify` (unlike `js/main.js`, which passes the full store module). Because the desktop Waveboard/Analytics views are idempotently mounted and refresh only via the `store.subscribe` fan-out triggered by `notify()`, a manual Recompute Scores click correctly rewrote `score_snapshots` in IndexedDB but never told the already-mounted view to re-read it — making cause (1)'s fix appear to do nothing during the first live-verification attempt.
- **Fix:** (1) `_computeS1Periodic` now only increments `expectedPeriods`/`completedPeriods` when a period has fully elapsed (`pEnd <= ctx.evaluationDate`) OR already has a completion; the still-open current period is excluded from both until it elapses. (2) `js/views/settings.js` added `notify` to its existing static import from `../state/store.js` and calls it unconditionally in `recomputeScores`, removing the fragile `store && typeof store.notify === 'function'` guard and the dead `store` destructure — fixing the class of bug for any current/future shell, not just `js/desktop.js`'s one object literal.
- **Files changed:** js/domain/scoring.js, tests/unit/scoring.test.js, js/views/settings.js, tests/integration/settings.recomputeScoresNotify.test.js
- **Why not caught:** No existing test covered `computeS1`'s still-open-current-period boundary (only elapsed-period cases were tested). Separately, no existing settings test mounted `Settings` with a store object shaped like `js/desktop.js`'s (missing `notify`) — every existing settings integration test passed the full real store module namespace, so the wiring gap was structurally untestable by the prior suite.
- **Recurrence guard:** regression tests at tests/unit/scoring.test.js — `describe('computeS1 — weekly cadence periodic boundary (s1-weekly-period-premature)')` + monthly equivalent (4 tests: premature-fail excluded, elapsed-miss still penalizes, mid-period-already-completed unaffected, monthly parity) — and tests/integration/settings.recomputeScoresNotify.test.js (1 test: mounts Settings with a desktop-shaped store missing `notify`, spies on `store.subscribe`, asserts the spy fires after Recompute Scores) — plus this knowledge-base entry, so a future Phase-0 match flags both "denominator counts a still-open period" and "reactivity signal routed through an optional caller-injected DI param instead of the static module export" as recurring defect classes.

## waveboard-wave-row-not-pinned — waveboard wave-header row still scrolls with the grid instead of staying pinned like the habit-name column

- **Date:** 2026-09-18
- **Error patterns:** wave header row not sticky, wave-header scrolls with grid, position sticky no-op, colspan sticky not working, td sticky left:0 does nothing, sticky fix shipped but doesn't work, live DOM missing span after fix
- **Root cause(s):** TWO unrelated causes stacked on the same bug report. (1) code — the wave-header `<td>` in `buildWaveboardRows()` (`js/views/desktop/waveboard.js`) uses `colspan` spanning every column, making its box exactly as wide as the whole scrollable table; `position: sticky; left: 0` applied directly to that `<td>` (added by an earlier fix, commit `55780e2`) computed correctly per `getComputedStyle` but produced zero visual movement, because a colspan'd cell already equal to its containing block's width has no "room" for sticky's algorithm to shift it. The working `.waveboard-sticky-column` cells stick fine because they're exactly one column wide. (2) config/process — that earlier fix (and this session's fix, before self-correction) touched `css/desktop.css` without bumping `APP_VERSION`, violating the project's own documented PATCH-bump policy; `sw.js` serves non-`/js/` assets cache-first, so a previously-activated service worker would never pick up the corrected CSS regardless of code correctness. (3) NOT a code cause at all, but the actual explanation for the FIRST two "still broken" human-verify failures in this session: the user was checking the app's deployed GitHub Pages site, which is built from a branch the fix had not yet been pushed to — an environment-mismatch false negative, not a defect.
- **Fix:** (1) Wrapped the wave-header label text in an inner `<span class="wave-header-label">` and moved `position: sticky; left: 0` from the outer colspan `<td>` onto that span (outer `<td>` keeps background/font styling, gets `padding: 0`) — mirrors how the working sticky column behaves. (2) Bumped `APP_VERSION` 0.5.0 → 0.5.1 so `sw.js`'s `activate` handler invalidates the stale CSS cache. (3) No code fix — closed by pushing the already-correct local commits to origin so the deployed site actually received them.
- **Files changed:** js/views/desktop/waveboard.js, css/desktop.css, tests/unit/views/desktop/waveboard.builders.test.js, tests/unit/views/desktop/waveboard.css.test.js, js/util/version.js
- **Why not caught:** The original sticky fix's own regression test only regex-checked CSS text for `position: sticky` + `left: 0` presence — it had no way to detect that a colspan'd cell renders the rule as a no-op in a real browser, so a fully "passing" test suite shipped a visually broken fix. Separately, no gate exists (or reasonably could exist, being outside a project's own codebase) checking that a CSS-touching commit also bumps `APP_VERSION` per the documented policy — this was a process gap, not a testable code gap.
- **Recurrence guard:** regression test at tests/unit/views/desktop/waveboard.builders.test.js — asserts the wave-header `<td>` wraps its label in an inner `span.wave-header-label` (a DOM-structure assertion, not a CSS-text assertion) — plus this knowledge-base entry, so a future Phase-0 match flags "`position: sticky` applied directly to a colspan-spanning table cell" as a recurring no-op pattern, and flags "verify which environment (local dev server vs. deployed site, and whether the fix was actually pushed) before trusting a live-verification 'still broken' report" as a standing debugging habit for this project, given this same environment-mismatch false negative has now occurred twice (once in `s1-weekly-period-premature`, once here).
