## Symptoms

- **Expected behavior:** The wave-number/wave-name header row in the desktop waveboard heat-map should stay pinned to the left edge during horizontal scroll, matching the already-sticky habit-name column. This was supposedly fixed by quick-260917-o9h (commit `38c2393`), which added a scoped sticky rule for `.waveboard-grid .analytics-wave-header td`.
- **Actual behavior:** The wave-number/wave-name row still scrolls away horizontally with the rest of the grid content when the user scrolls right; only the habit-name column stays pinned in place.
- **Error messages:** None reported — this is a visual/CSS layout defect, not a JS exception.
- **Timeline:** User has not specifically re-verified this since quick-260917-o9h (commit `38c2393`, 2026-09-17) landed — this is effectively the first real check. Note: quick-260917-n8p (commit `dd29965`, also 2026-09-17) changed the waveboard's week range from a fixed last-12-weeks to full history with horizontal scroll, landing around the same time as the sticky fix — worth checking whether that change altered the grid structure/markup in a way that broke the sticky rule's selector match or stacking context.
- **Reproduction:** Open `desktop.html`, navigate to Waveboard, scroll the heat-map grid horizontally. Observed: the wave-number/wave-name row moves with the scroll instead of staying fixed at the left edge, while the habit-name column correctly stays put.

**User-reported nuance to confirm during investigation:** user said this happens on "both mobile and desktop" — but architecturally the waveboard view only exists on the desktop shell (`js/views/desktop/waveboard.js`, wired only via `js/desktop.js`'s `#waveboard` route; `index.html`/`js/main.js` has no waveboard route at all per this project's two-shell architecture). ## Resolution

root_cause: "TWO confirmed, additive causes (AND-gate fired — see Current Focus): (1) code — the wave-header row's <td> in js/views/desktop/waveboard.js's buildWaveboardRows() spans every column via `colspan` (habit-name column + all week columns), making its box exactly as wide as the entire scrollable table. `position: sticky; left: 0` applied directly to that <td> (css/desktop.css, `.waveboard-grid .analytics-wave-header td`, added in commit 55780e2) computes correctly (`getComputedStyle` confirms `position: sticky; left: 0`) but produces zero actual movement when the container scrolls, because the cell has no 'room' within its own box for the sticky algorithm to shift it — empirically verified via Playwright/Chromium (left offset moved from 10px to -290px, i.e. tracked scroll exactly, when scrollLeft was set to 300px). The single-column `.waveboard-sticky-column` cells work correctly because they are exactly one column wide, not colspan-spanned. (2) config/process — neither commit 55780e2 (the original ineffective fix attempt) nor this session's fix (before this correction) bumped `APP_VERSION` in js/util/version.js, despite both changing css/desktop.css. Per this project's own documented policy (README.md 'Bumping the Version', VERSIONING.md), any CSS change requires a PATCH bump because sw.js's fetch router serves non-`/js/` assets (including css/desktop.css) cache-first — a browser with a previously-activated service worker will keep serving the OLD cached CSS forever, regardless of on-disk fixes, until the SW cache name (`habits-${APP_VERSION}`) changes and the `activate` handler deletes the stale cache. This independently explains why the ORIGINAL 55780e2 attempt could never have shown a visual effect for a returning user even though its CSS text was syntactically fine (a different, unrelated defect from cause 1)."
