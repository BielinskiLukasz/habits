## Symptoms

- **Expected behavior:** Browsing History for a date long before any habit was ever created/seeded (e.g. 2025-12-10, a date the app's real imported habit data never covers — earliest real data starts 2025-12-30) should show no applicable habits, or at least should not show habits that didn't exist yet.
- **Actual behavior:** The 8 default starter habits from `seed/habits.json` (all with `startDate: null`, `status: "active"`) appear as applicable on that date, each rendered with status "–" (no log recorded) and full Toggle/Skip/Fail swipe-action controls, as if they were live daily habits on that day.
- **Error messages:** None — this is a logic/display bug, not a thrown error.
- **Timeline:** Discovered this session while spot-checking History after regenerating `data/habits-import-2026-09-17.json` (an unrelated data-import quick task). Not caused by that import — none of the 66 real imported habits have `startDate: null`.
- **Reproduction:** Fresh or existing install with the default seed catalog present (8 starter habits, `startDate: null`) → open History view → navigate to any date before the app was ever used (e.g. years in the past) → seed habits still show as applicable with empty/uncompleted status and full action controls.

## Investigation already performed this session (read-only, no fix applied)

- `js/domain/cadence.js` `appliesToday()` (~line 99-103): the CATALOG-07 future-scheduling guard is
  ```js
  if (habit.startDate && habit.startDate > date) {
    return false;
  }
  ```
  This only blocks when `startDate` is truthy. `seed/habits.json`'s 8 starter habits all have `startDate: null`, so the guard is a no-op for them — the cadence resolver (`daily`, `weekly`, etc.) is consulted for literally any date, including dates from before the app existed.
- `js/views/history.js` `render()` (~line 234-236) has a second guard intended to catch this case:
  ```js
  for (const habit of allHabits) {
    // Skip habits created after the selected date (didn't exist then).
    if (habit.createdAt && habit.createdAt > date) continue;
  ```
  This is also a no-op for seed habits: confirmed via `grep`/`Read` of `js/io/seed.js` (~lines 150-220, the first-run seed-insert transaction) that the code writes `tx.objectStore('habits').put({ ...h, slots: normalizeSlotsToArray(h.slots) })` — the habit row is written verbatim from `seed/habits.json`, which has no `createdAt` field, and no other code path in `js/io/seed.js` sets `createdAt` on the habit row. Only an `events` row (`type: 'seed:createHabit'`, `at: new Date().toISOString()`) records a timestamp, but that's a separate `events` store row, not read back onto `habit.createdAt` anywhere in `history.js` or `cadence.js`.
- Confirmed (via `node -e` against `seed/habits.json`) that all 8 seed habits have `startDate: null` and `status: 'active'`.
- Confirmed the 66 real habits in `data/habits-import-2026-08-27.json` and `data/habits-import-2026-09-17.json` all have a real `startDate` string — this bug does not affect them, and does not affect the import work done earlier this session.
- Note: `js/io/seed.js` (~line 187, ~line 251) already computes an `effectiveFrom = h.startDate ?? '0000-01-01'` sentinel when writing the initial `habit_versions` row — that sentinel exists specifically so `getHabitVersionAtDate` can still resolve a name/version for very old dates. Any fix must not break that sentinel's compound-key uniqueness guarantee (`[habitId, '0000-01-01']` must stay distinct from any real edit's `[habitId, editDate]`).
