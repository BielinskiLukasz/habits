<current_state>
Mid-debug-session, not mid-phase. User reported: editing a scheduled (future-dated) habit's start date in the Catalog screen doesn't save. Ran `/gsd-debug`, session slug `catalog-start-date-not-saving`, session file `.planning/debug/catalog-start-date-not-saving.md`.

Root cause confirmed: `js/state/apply/editHabit.js::handleEditHabit` never destructured `startDate` from `event.payload`, so it silently kept the old value regardless of what the Catalog edit form sent (Catalog UI was already correct — `js/views/catalog.js` / `js/views/catalog/builders.js` send `startDate` correctly and always have). Long-standing bug since v1.0 Phase 4, only became visibly actionable once v1.1 shipped scheduled habits.

Fix applied (TDD): added `startDate` to the destructured payload fields in `editHabit.js` and `if (startDate !== undefined) habitRow.startDate = startDate;`, matching the existing per-field override pattern used for `name`, `wave`, `cadence`, etc. Added 2 regression tests to `tests/integration/apply.editHabit.test.js`. Full suite (`node --test tests/`) passes: 985 tests, 0 failures.

**The fix is implemented and test-verified but NOT yet committed and NOT yet human-verified in the live app.** The debug session manager reached a `human-verify` checkpoint and is paused there — it cannot call `AskUserQuestion` itself (nested-subagent limitation), so the orchestrating session must relay the checkpoint to the user and then resume the session manager with the answer.
